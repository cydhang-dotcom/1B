# copreg 流程与 URL 路由

copreg.html 是一个六步向导，每一步在地址栏里有一个 hash，但**地址栏是只读的**：
刷新时忽略它（落点只按本地进度证据算），页面开着时手敲 / 前进后退也改不动页面 ——
它只反映「当前在第几步」。步骤映射写在 `src/copreg/stepRoute.ts`。

> **多主体**：一个用户最多可以有 5 份申请，每份各有自己的步骤 / 解锁范围 / 订单 / 委托单 / 申报表。
> 地址栏**只反映「当前主体」在哪一步，不带主体 id**；主体身份由本地 `activeAppId` 决定，
> 刷新回到上次那个主体，切主体时地址栏跟着改成新主体的步骤。存储键与规则见
> [copreg-multi-app.md](copreg-multi-app.md)。

| # | 内部步骤名 | URL | 渲染组件 | 什么时候解锁 |
|---|---|---|---|---|
| 1 | `survey` | `#survey` | `components/SurveyStep.tsx` | 始终 |
| 2 | `proposal` | `#proposal` | `components/ProposalStep.tsx` | 始终（有方案可回看）；**订单已支付后 02 服务套餐与 03 自选增值服务转为不可选**（付款后改档会让页面价格与那笔订单对不上） |
| 3 | `payment` | `#payment` | `components/AgreementAndPaymentStep.tsx` | 第 1 步接口返回委托单号后（第 2 步只是展示，点「前往支付」即到） |
| 4 | `group` | `#group` | `components/ServiceGroupStep.tsx` | 支付成功后 |
| 5 | `fill_details` | `#fill-details` | `components/RegistrationDetailsStep.tsx` | 支付成功后（`#paid` 的「申报资料填报」，或服务群页里的入口） |
| 6 | `progress` | `#progress` | `components/ProgressAndReviewStep.tsx` | 填报之后 |

`agreement` 是已废弃的步骤（协议确认并进了支付），没有任何入口，它的 hash 也归到 `#payment`。

第 3 步内部有**两个界面**：待支付与支付成功。它们各自一个 hash：

| 界面 | URL | 判据 |
|---|---|---|
| 待支付（协议 + 立即支付） | `#payment` | `showsPaidView` 为假 |
| 支付成功（委托代办已生效） | `#paid` | `showsPaidView(服务端查单确认已支付, 申报资料已提交)` —— 只有这两条依据：查单说已支付，或资料已提交（后者本身就说明付过款） |

**本地那份 `order.status` 不是依据**（2026-09 改）：**有委托单号 ≠ 已支付** —— 单号是第 1 步生成方案时
服务端就建好的，只证明建过单；本地摘要还可能过期、或是上一笔留下的。所以：

- 只要手上有单号，**进页面就查一次**支付状态（同一单号一次会话只查一次，见 `orderStatusCheck.ts`）；
- 查回 `status='1'` → 标已支付，补单号 / 支付时间 / 手机号，地址栏与第 3 步翻成支付成功界面；
- 查回 `status='0'` → **把本地那份 paid 改回 pending 并清掉单号 / 支付时间**（不然上一笔的 paid 会一直骗人）；
- 查不动（路径没配 / 超时 / 网络不通 / 响应认不出）→ 不动本地结论；
- **响应里的 `scbUuid` 为空 → 这条开户记录已经被后台删了**（正常单子建单时服务端就写了 `scbUuid`）：
  这不是「未支付」，而是这份申请在服务端不存在了。App 会弹一个不可取消的提示
  「**该主体已被后台删除，请重新提交**」，点「重新提交」后：清掉该主体的三份方案存档
  （问卷 / 诊断结果 / 委托单号）与申报表草稿 → **重开一份申请**（新 appId，落第 1 步）→
  **把旧的 `plan_form` 填进新的那份**（问卷 + 套餐 + 自选增值服务带过去，诊断结果与单号不搬，
  它们跟着新申请走会前后矛盾）。查不动时**绝不能**报「被删」：网络抖一下就把用户的申请清掉不可接受。
- 所以「有单号但还没查单」的那一瞬间，页面显示的是**待支付**：诚实优先，代价是已支付用户刷新会看到
  一瞬待支付再翻成支付成功（地址栏同样先 `#payment` 再 `#paid`）。

自检：`node .mcp-work/verify-entry-paid-query.mjs`（12 项，真机 —— 三个场景：本地 paid + 查单未支付 →
落 `#payment` 且本地改回 pending；本地未支付 + 查单已支付 → 落 `#paid` 并补单号；接口 500 → 不动本地结论）。

支付成功界面「服务进度状态与办理清单」里第一项（申报资料填报）的主按钮是**「申报资料填报」**，
**在新标签页打开**第 5 步（2026-09 改；提交过之后同一个按钮变成「查看/修改申报资料」，行为一样）。
第 4 步服务群仍然解锁、导航里可直达，但不再是这一页的下一步（付完款该做的是填申报资料）。
弹窗被浏览器拦掉时退回同页跳转，按钮不会变成没反应。

### 新标签页怎么落到第 5 步：`?open=fill-details` 深链

新标签页打开时**地址栏不指挥页面**（见前面「地址栏只读」），所以光带 `#fill-details` 它会按本地证据
落回第 3 步。按钮打开的地址因此带一个**显式的意图参数**：

```
copreg.html?open=fill-details
```

四条约束（都在 `src/copreg/stepRoute.ts`，纯函数、可离线自检）：

1. **只认白名单值**（现在只有 `fill-details`），不认识的一律忽略；
2. **能不能真的进第 5 步还要看本地证据**：只有「已支付（本地摘要 paid）或申报资料已提交」才放行 ——
   否则这条链接就成了绕过支付直接进填报页的入口（`allowsFillDetailsIntent`）；
3. **参数用过就抹掉**（挂载后 `replaceState` 只留 `{pathname}#fill-details`）：刷新、复制、转发出去
   的地址不会再触发跳步。
4. **落点只到第 3 步**：`fill_details` / `progress` 都是**会话级浏览位置，不写进主体记录**
   （`canPersistStep` / `MAX_PERSISTED_STEP = 'payment'`）——「进度」最大到 `payment`，
   第 5 步只能从支付成功页进。所以：深链进来的那一页刷新一下就回到支付成功界面；
   读存档时若发现写着 `fill_details`（老版本写进去的）也收口回 `payment`（`clampPersistedStep`）。

自检：`scripts/check-step-route.ts`（12 条深链断言 + 登记上限）、`npm run check:entry`（已支付+参数 → 落第 5 步；
未支付+参数 → 忽略仍落第 3 步；不认识的意图值 → 忽略）、`.mcp-work/verify-paid-cta.mjs`（12 项，真机：
**真实鼠标手势**点按钮 → `window.open` 真开成功（不是 null，否则会误走兜底把原网页跳走）、当前页留在 `#paid`、
新标签页真的落在填报页、参数已抹掉、**主体记录里的步骤仍是 payment**、**刷新那一页回到支付成功界面**）。

已支付界面上「订单编号 / 支付时间」两格的数据来源是**查单响应**（`orderNo` / `payTime`）；
「经办人姓名 / 经办联系电话」**以申报资料里填的「联系人」为准**（`registration/contactInfo.ts`
＋ `useRegistrationContact`，读的是当前主体那份 `banbu-registration-{appId}` 草稿）：

- 联系人的姓名 / 电话填了就取联系人的（两项分开判断，只填一项时另一项退回订单上的值）；
- 联系人还没填时退回订单上那份：电话取查单回来的 `mobile`，姓名一直没有别的来源，显示破折号；
- 填报页是**新标签页**打开的，所以本页监听 `storage` 事件（那边一保存草稿就跟着更新），
  另外 `focus` / `visibilitychange` 时也重读一次；同标签页从填报页返回时组件重新挂载，自然读到新的。

## 刷新落在哪一步：从后往前看进度证据

刷新时先算「**最远做到哪一步**」，判断顺序是**从后往前**（后面的证据优先）——

| 已知证据 | 最远步骤 | 解锁范围 |
|---|---|---|
| 第 5 步申报资料已提交（草稿 `status === 'submitted'`） | 第 3 步的**支付成功界面**（hash `#paid`） | 六步全解锁（进度页仍解锁、手敲 `#progress` 可达） |
| 订单已支付（异步查单确认；首帧不知道） | 第 3 步的**支付成功界面**（hash `#paid`） | 到第 4 步（服务群可直达但不默认跳） |
| 有委托单号（`1b_copreg_plan_record`，第 1 步建单时给的） | 第 3 步 协议与支付（**待支付**界面，除非查单确认已支付 / 申报资料已提交） | 到第 3 步 |
| **有接口返回的诊断结果**（`1b_copreg_plan_report`） | 第 2 步 方案与报价 | 到第 2 步 |
| 只有问卷存档（`1b_copreg_plan_form`）或什么都没有 | 第 1 步 业务信息调研 | 只第 1 步 |

> 表里的键名是**多主体的 per-app 键**（`1b_copreg_app:{appId}:plan_*`）。单主体时代的全局键
> （`1b_copreg_plan_form/_report/_record`、`banbu-registration-20260913-v1`）**2026-09 起不再读**：
> 「老存档迁移」整段逻辑已删除，没有主体列表就是全新一份申请（落第 1 步），旧键不读、不搬、也不删。

> 三处都曾经写错。第一处只看「有凭据 → 第 3 步」，于是**申报资料都填完了的人一刷新
> 又被送回支付页**；第二处只看「有问卷存档 → 第 2 步」，于是**本地只有 `1b_copreg_plan_form`
> 的人一刷新就跳进方案页**——可方案页的行业内容全来自诊断接口，那时它只有一份本地模板；
> 第三处把「已提交」的落点定成第 6 步进度页，于是**提交完回的是 `#paid`、刷新却掉到进度页**。
> `progressRouteOf()` 现在按上表从后往前判断：判据是「有诊断结果」而**不是**「有问卷存档」，
> 已提交则落支付成功界面。
>
> 「已提交 ⇒ 支付成功界面」不等于假装已支付：填报页只有支付成功页上的入口能进，
> 所以那本身就说明付过款（`showsPaidView(orderPaid, detailsSubmitted)`）。这样刷新时
> **不用等查单**，不会先闪一屏「待支付」，查不动时也不会一直停在那儿。

> 这个核实走 `orderStatusCheck.ts` 的单飞闸门（同一单据号只请求一次）。**不要**把它简化回
> 「查过就记一个 ref」：dev 的 StrictMode 会「挂载 → 清理 → 再挂载」，第一轮结果被丢弃，
> 闸门若在那时就记账，第二轮不会再查 —— 已支付就永远不生效（真机上踩过）。

**已支付是异步才知道的，所以落点会补一次**：首帧只能按本地证据算（可能先落在第 2 步），
查单回来说已支付时，如果用户**还停在首帧那一步**（没自己走动过），就把落点补到支付成功界面
（`advanceOnPaid`）；他自己走开过就不动他 —— 他可能是特意回来看方案的。

> 首帧落点决策在 DEV 下会打一条 `[copreg] 首屏落点（忽略地址栏 hash）` 日志（地址栏 hash / 有无问卷存档 / 有无诊断结果 /
> 有无委托单号 / 申报是否已提交 / 解锁范围 / 落点）。本地凭据缺失导致落点偏早时，看这一行就知道卡在哪条证据上。
> 生产构建里这条日志会被折叠掉。

## 第 1 步 · 建单与改方案是两条路（判据：本地有没有委托单号）

问卷页那个「生成需求方案」按钮按**本地有没有 `1b_copreg_plan_record`** 分流：

| 本地状态 | 走哪条 | 验证 | 服务端 |
|---|---|---|---|
| 没有委托单号（第一次，或重置过问卷） | `handleSurveySubmit` → `generatePlanReport` | 腾讯行为验证码（发短信时）**+ 手机短信验证** | `POST /api/company-plan/diagnose-architecture`，**建单**并返回 `recordId` |
| 已有委托单号（建过单，回第 1 步改问卷） | `handleSurveyModify` → `modifyProposal` | **只过腾讯行为验证码** | `POST /api/company-plan/modify-proposal`，带 `recordId` 改这张单，**不建新单** |

为什么手机号只验一次：手机号是**建单那一次**验过的，同一张单上沿用即可 —— 改的是这张单上的问卷内容，
不是换个人来下单。重开一单（重置问卷会清掉单号）时又会回到要短信验证的那条路，口径与「建单才验手机号」一致。

两条路的收尾是同一段（`App.tsx` 的 `runPlanSubmit`）：存本次问卷 → 存返回的报告与单号 →
作废上一份诊断结果 → 清上一笔的付款痕迹（见下一节）→ 落到方案页。**唯一的差别在单号那一份存档**：

- 第一次生成方案（本地没有单号）：清掉旧的（那时也不会有），接口会建一张新的；
- 改方案：**不清** —— 它正是这次改动要带上去的 `recordId`，清掉就把「下单 → 查单」那条链剪断了。

失败显在哪也不同：手机验证那条挂在验证弹框里（改验证码原地重试），改方案这条没有弹框可挂，
走问卷页的 toast；用户主动关掉腾讯验证码不算失败，静默留在问卷页（`CaptchaCancelledError`）。

**弹框顺序：行为验证成功之后才弹下一个弹框。**改方案这条一共就两个弹框：先腾讯行为验证码，
用户点通过之后才盖「AI 推演中」生成弹框（由 `modifyProposal` 的 `onCaptchaPassed` 回调触发），
然后才发 `modify-proposal`。顺序反了生成弹框（`z-[60]`）会把验证码盖在下面，看着像卡住 ——
那个弹框是给等接口用的，不是给等验证码用的。手机验证那条路本来就是这顺序：
验证码在「获取验证码」那一步弹，生成弹框在提交短信验证码之后才开。

自检：`scripts/check-plan-modify.ts`（22 项，源码级契约 —— 路径、body 只有 `recordId` + `formData`、
无 `phoneNumber`、四件套在 query、单号兜底、弹框顺序）、`.mcp-work/verify-modify-proposal.mjs`（20 项，真机 ——
断言不弹手机框、不发短信、验证码未过时不弹生成弹框也不发请求、过了才盖、打的就是 `modify-proposal`、
单号存档没被作废）。

## 第 1 步重新生成方案 = 新一单：上一笔的付款痕迹必须清掉

`showsPaidView(已支付, 申报资料已提交)` 的第二个入参是主体记录上的 `isDetailsSubmitted`，它是**上一笔单**的
事实。第 1 步重新提交问卷时服务端会给一个**新的委托单号**，所以旧单的「已付 / 申报资料已提交」对新单不成立：

- `handleSurveySubmit` 在 `clearPlanReportFor` / `clearPlanRecordFor` 之后，把这份付款痕迹一起清回新单状态
  （`isDetailsSubmitted: false`、`status: 'pending'`、清空 `orderNo` / `paidAt`；手机号与本次新算的金额 / 套餐名保留），
  runtime 的 `order` 与主体记录的 `order` 两处都要写。
- 不清的后果（用户报过，已复现）：**同一个主体以前提交过一次申报资料（哪怕之后回第 1 步重开一单），
  之后每一单的第 2 步都会被判成已支付** —— 方案页 02 区写「订单已支付 · 套餐已锁定」、弹出「付款后改档
  会让页面价格与那笔订单对不上」，套餐卡与加购全点不动；而这时服务端查单还在说「未支付」。
  `activeApp.order.status === 'paid'` 同源：它也吃上一笔的 `paid`，重开一单会把方案页一起锁住。
- 真付过的单**不会因此丢状态**：进页面 / 进第 3 步的异步查单会重新问一次服务端，`status === '1'` 就补回「已支付」。
- 自检：`node .mcp-work/verify-resubmit-resets-paid.mjs`（13 项，真机 —— 走完第 1 步 → 造出「已提交 + 已支付」
  的旧状态 → 回第 1 步重开一单 → 断言方案页未被锁、存档里两处痕迹都清掉）。把这次的重置去掉，
  这个脚本会挂 5 项。

## 地址栏只读：它只反映当前步骤

**没有任何地方会解析 hash 来决定去哪一步**（`stepOfHash` / `resolveStep` 已删除）。规则只有两条：

1. **刷新 / 打开链接时忽略地址栏的 hash**：落点由 `progressRouteOf` 按本地证据算，
   随后 App 把地址栏**改写成真实步骤**。为什么：收藏 / 转发出去的链接会过期、也会在别人手里 ——
   带 `#progress` 的链接到了别人机器上没有那份申报表，带 `#paid` 的链接既不是本人付的款、
   也可能早就不成立；照 hash 进只会把人带进一份空壳页面。**谁该看到哪一步，只有本地证据说了算。**
2. **页面开着时改地址栏也没用**：手敲 hash、浏览器前进 / 后退都会被 `hashchange` 监听
   **立刻改回当前步骤**，页面原地不动。跳步只能点页面上的按钮（「上一项 / 下一步 / 返回…」）。

写地址栏一律走 `history.replaceState`，**不压历史条目** —— 用户按浏览器后退是离开这个页面，
而不是回到上一个步骤（步骤历史对这个向导没有意义）。地址栏里那条链接依然可以复制，
但它只是「当时在第几步」的记录：换个人、过一天打开，仍按**他自己的**本地证据落点。

## 写进地址栏的 hash 是什么样

`#survey` / `#proposal` / `#payment` / `#paid` / `#group` / `#fill-details` / `#progress`
（`fill_details` 内部名带下划线，URL 里换成连字符）。已废弃的 `agreement` 归到 `#payment`。
**外面怎么写都不影响落点**，所以不需要解析容错。

## 「微信扫码咨询」弹窗（三处共用）

第 3 步的按钮、填报页的同一个弹窗、落地页提交成功后的客服码弹窗，走的是**同一份实现**
（`src/utils/customerServiceQr.ts` 判断 + `src/hooks/useCustomerServiceQr.ts` 请求）：

1. **先查询**：弹窗打开时才去问服务端，地址 `{DOC_HOST}/xcx/yqt-co/user/{shareUserUuid}/get`
   （分享人来自 URL 的 `?shareUserUuid=`）；查询期间显示「正在获取专属顾问二维码…」，
   不会先闪一张兜底图再换成专属码。
2. **再判断**：响应里有 `perShareEwmFile` → 用 `{DOC_HOST}/doc/uuid/{file}/get` 上的专属企微码；
   没有 / 不是字符串 / 超时 / 网络不通 / 没分享人 → 一律回落
   `https://www.ibanbu.com/image-yqt/customer-service-qr.png`（通用兜底图，绝对地址，换域名也不 404）。
3. **后显示**：`<img>` 永远拿到一个可用地址，不会出现裂图或空二维码。

自检：`npx tsx scripts/check-customer-service-qr.ts`（20 项，覆盖地址拼接、转义、
以及八种「拿不到」都必须回落兜底图）。

## `#paid` 比别的 hash 更严格

别的 hash 只表达「想去哪一步」，`#paid` 表达的是**事实**（已经付过款）。支付状态是服务端
说了算的，前端没有凭据，所以：

1. 首帧拿 `1b_copreg_plan_record` 的 `recordId` 调**查单接口**（与地址栏无关：
   只要有委托单号且还不知道已支付就问一次）
   （`GET {DOC_HOST}/xcx/yqt-co/wx-pay/open-acc/query/pay?busUnionId=…`，
   即 `src/payment/client.ts` 的 `queryOrder` + `src/copreg/paymentStatus.ts`），
   状态判定复用 `mapOpenAccState`；
2. 只有查单返回 `status='1'` 才进「支付成功」界面，并把服务端给的 `orderNo` 显示为订单编号、
   `payTime` 作为支付时间、`mobile` 补上「经办联系电话」，同时解锁第 4 步。
   这三项都只能从查单拿：**手机号按约定不落本地**（第 1 步验证完只在内存里），
   订单号与支付时间也只有服务端知道 —— 少了这一步，重新进入页面时那几格就是空的；
3. 其余一律当没付：`status='0'`、不认识的 status、响应缺 status、超时、网络不通、路径还没配
   → 地址栏收口回 `#payment`，用户停在待支付页照常付款。**认不出的响应绝不当已支付** ——
   宁可让人多点一次「立即支付」，也不能造出一个看着像已支付的界面；
4. 会话内手敲 `#paid` 而本地并没有确认过已支付 → 直接改回 `#payment`（下次刷新时首帧核实
   会再给一次机会）。

## 订单状态核实与「已经付过了」的自愈

本地存的凭据可能被清掉（换浏览器、隐私模式、手删 localStorage），而订单状态只有服务端知道。
所以：

1. **进页面时**：只要有确认单据号、且还不知道已支付，就先查一次订单状态（`queryOrder`）；
   服务端说 `status='1'` 就直接进「支付成功」并把单号 / 支付时间 / 手机号补上 —— 否则用户会被
   留在「待支付」页，一点「立即支付」就会被服务端拒。
2. **下单被拒时**：先补查一次状态。订单其实早已支付 → 直接按已支付处理（自愈）；
   确实没付 → 把服务端给的原因原样告诉用户。
3. **服务端的业务失败**：同一套 `reasons[]` 信封既可能出现在 200（前端解析器识别），
   也可能直接是 **HTTP 400**（HTTP 分支读响应体识别）——两条路都会把这句 `message`
   透出来给用户看，不再笼统报「返回 400 / 返回格式不正确」。

## 收银台（第 3 步的「立即支付」）

点击「立即支付」→ `POST {DOC_HOST}/xcx/yqt-co/wx-pay/open-acc/pay`，body 只有两个字段：
`{ payAmount: 页面上的实付金额（元）, busUnionId: 确认单据号 }`，响应里的 `codeURL` 就是
微信 Native 的 `code_url` 文本，前端自己渲染成二维码（`src/payment/PayQrCode.tsx`，不依赖
后端出图）。之后按 `busUnionId` 轮询查单，`status='1'` 才落「已支付」。

几点是刻意的：

- **没有「演示完成支付」按钮**：不付款就标成已支付是假的终态，接了真实接口就不能再留。
- **一次点击只发一次下单**：服务端没有去重键，重复下单会真的产生两个订单；过期换码走
  「重新出码」（同样是显式点击）。
- **查单网络抖动不卸载二维码**：只提示「查询暂时不通，二维码仍可继续扫」，否则用户正扫着码
  界面就白了。
- 金额是前端传的，**服务端必须按 `busUnionId` 复核价格**（见 `payment/client.ts` 的注释）。
- **《委托代理服务协议》的甲乙方**：甲方 = **第 1 步验证过的经办手机号**（`order.contactPhone`，
  刷新后由查单响应的 `mobile` 补回来），乙方 = **上海班步企程科技有限公司**。
  甲方原来用的是 `order.contactName` —— 那个字段**没有任何地方采集**（填报页的「经办人姓名」
  只在前面的清单里显示破折号），协议上一直印着「＿＿＿＿」，等于没写委托方是谁。
- **协议正文 = 《班步一企通服务委托单》**（2026-09 换稿）：弹框里的正文已由「第一条~第四条」
  那版换成委托单全文 —— 效力声明（只列于本文不视为已购买、以订单/服务确认记录为准）+
  一、服务内容及标准价格（注册代理 600／户次、税务财税托管 2500（小规模）/3000（一般）／年、
  零申报 600／年、人力资源 20 元／人／月、政府补贴按到账金额 15%/10% 分段累进）+
  二、双方责任与服务办理（5 条有序列表）+ 三、保密与信息保护 + 四、变更、终止与结算 +
  五、确认方式。**弹框里不再写具体金额**（`plan.finalPrice` 只在收银台各处显示），
  金额口径统一由「以双方确认的订单为准」承接。受托方主体全篇统一为**上海班步企程科技有限公司**

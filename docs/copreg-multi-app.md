# 多主体申请（S3）

一个用户可以有**多个企业设立申请**（产品确认：最多 5 个），每个主体各自一套问卷、方案、
委托单、订单、申报资料与进度。本文记录**存档键空间与迁移规则**；代码本体是
`src/copreg/applications.ts`（纯逻辑，`scripts/check-applications.ts` 53 项离线自检）。

> 进度：**S3a（模型 + 存储键 + 迁移）、S3b（App 状态收敛）、S3c（顶栏切换/新增/改名/作废 + 各步骤按主体接线）、
> S3d（支付与路由按主体、验证与文档）均已落地**。老存档在首次进入时自动迁移成「主体 #1」，用户无感。

---

## 一、键空间

| 键 | 内容 |
|---|---|
| `1b_copreg_apps_v1` | **主体列表**：每个主体一条 `ApplicationRecord`（id / 名称 / 创建与更新时间 / 当前步 / 解锁步 / 订单摘要 / 是否已提交申报资料） |
| `1b_copreg_active_app_v1` | 上次停留的主体 id（刷新按它恢复；**地址栏不带 appId**） |
| `1b_copreg_app:{id}:plan_form` | 该主体「填写的」：问卷 + 套餐 + 自选项（`planDraft.PlanForm`） |
| `1b_copreg_app:{id}:plan_report` | 该主体「返回的」：诊断结果（`PlanSuggestion`） |
| `1b_copreg_app:{id}:plan_record` | 该主体的委托单凭据 `{ recordId }` |
| `banbu-registration-{id}` | 该主体的申报资料表（第 5 步整份表单） |

旧的全局键（`1b_copreg_plan_form` / `_report` / `_record`、`banbu-registration-20260913-v1`）
**只留给迁移**，迁移成功后删除。

键工厂在 `applications.ts`：`planFormKey(id)` / `planReportKey(id)` / `planRecordKey(id)` /
`registrationKey(id)`；`planDraft.ts` 提供按主体读写的 `loadPlanDraftFor` / `savePlanFormFor` /
`savePlanReportFor` / `savePlanRecordFor` / `clearPlanDraftFor`（旧的全局函数保持原样，S3b 再切）。

## 二、业务规则（产品确认）

| 规则 | 落点 |
|---|---|
| **最多 5 个主体** | `MAX_APPLICATIONS = 5`；`addApplication` 到顶返回 `{ ok:false, reason:'limit' }`，UI 据此把「新增」置灰并说明 |
| **作废仅本地** | `discardApplication` 只删本地主体与存档，**不调任何接口**。注意：服务端那条 `recordId` 仍然存在，本地丢弃 ≠ 服务端撤单 |
| **已支付不可作废** | 订单摘要 `status === 'paid'` 时返回 `{ ok:false, reason:'paid' }` |
| **最后一个作废后补空白主体** | 列表永远不为空，避免出现「没有任何主体」的空壳界面 |
| **作废当前主体自动切走** | 切到剩下列表的第一个 |
| **主体之间不关联支付状态** | 每个主体各自一份订单摘要与 `recordId`；查单、下单、解锁都按各自的主体算 |
| **手机号不复用** | 新增主体**不预填**手机号；「同一手机号不能建第二个主体」由**服务端**在诊断接口拦（前端把服务端的原文显示在手机验证弹框里），以保持「手机号不落本地」的约定 |
| **名称可自定义** | 默认按 `申报表 basic.names[0]` → 诊断 `companyNameProposal` → 截断的 `companyDesc` → `企业设立申请（主体 N）` 派生；顶栏可改名（只落本地） |
| **申报资料按主体提交** | 仍走现有 `open-info { busUnionId, var2, savaType }`，每个主体用自己的 `recordId` |

## 三、老存档迁移

`planLegacyMigration(storage)` 只看不写，`applyLegacyMigration(storage, plan)` 才落盘：

1. 已经有主体列表（`readApplicationsState` 读得出来）→ **不迁移**，直接跳过；
2. 否则读四份旧键；一份都没有 → 不迁移（由 `ensureApplicationsState` 建空白主体）；
3. 有旧键 → 建**主体 #1**：
   - 落点沿用旧证据（`progressRouteOf`：有诊断→第 2 步、有单号→第 3 步、已提交→第 3 步并全解锁）；
   - 名称按上面的派生规则取；
   - 四份旧值**逐键原样搬**到该主体的键上；
   - **主体列表最后写**：它是「迁移已完成」的标记 —— 先写它的话，后面某份存档写失败时
     下次会读到「已经有主体」而跳过迁移，旧键还在却再也不搬；
4. 写入全部成功后才删旧键（删不掉也不影响：下次因为已有列表而直接跳过）。

任何一步写失败（配额满 / 隐私模式）→ 整体放弃、**旧键一个不动**，下次进页面重试。
`ensureApplicationsState` 是统一入口：已有列表 → 收口（`activeAppId` 无效则沿用列表里的）；
有旧档 → 迁移；什么都没有 → 建空白主体。连空白主体都存不下时返回 `null`，调用方提示。

## 四、实现要点（已落地）

- **App 状态收敛（S3b）**：`App.tsx` 只留两份状态 —— 持久化的主体列表 `applications + activeAppId`，
  以及每个主体的运行时 `AppRuntime`（`Record<appId, AppRuntime>`：问卷 / 方案 / 诊断建议 / 委托单 /
  订单详情 / 登记摘要 / 服务群消息 / 进度时间线 / 进度页演示态）。
  当前步骤、解锁范围、订单摘要、名称、是否已提交都在**主体记录**里，所以「刷新回到哪一步」与
  「切主体」用的是同一份数据；`activeAppId` 落 `1b_copreg_active_app_v1`，刷新回到上次那个主体。
- **地址栏语义**：hash 只反映「**当前主体**在哪一步」，**不带 appId**；切主体时地址栏会改成新主体的
  步骤。主体身份只由本地 `activeAppId` 决定 —— 分享出去的链接不会指向别人的主体。
- **顶栏（S3c，版式对照参考实现）**：品牌块（图标 + 「企业注册向导」+ AI 徽标 +
  「智能设立与合规规划服务」）+ 右侧切换按钮（楼宇图标 + 当前主体名 + 多于一个时的「N个主体」+ 箭头）。
  下拉标题是「我的企业注册服务（共 N 个）」，每条一张卡片：名称 + 「当前办理」徽标、
  「套餐: X · ¥Y」、右上状态徽标，底部一行创建时间与「作废服务 / 已生效履约中」，
  最下面一个虚线框按钮「新增企业注册」（到 5 个置灰并写明「已达上限」）。
  **相对参考实现的两处必要差异**：到顶置灰（参考没有上限）、每条多一个「改名」
  （参考不能改名，但产品要求名称可自定义）。作废仍要**点两次确认**、已支付不给入口；
  顶栏不再画进度条（参考也没有）。
- **各步骤按主体接线（S3c）**：`RegistrationDetailsStep` / `AgreementAndPaymentStep` 接 `appId`，
  申报表读写走 `registrationStorageKey(appId)`；服务群消息、进度时间线、进度页演示态都按主体隔离，
  切主体不会串场。
- **支付按主体（S3d）**：订单状态核实的 checker 改成 **`Map<recordId, checker>`** —— 每个委托单号
  各自单飞，切主体互不影响，也不会重复查同一个单号；支付成功只解锁当前主体。
- **摘要回填**：`order.tierName` 是「下拉显示套餐」才加进摘要的，早于它的存档（含单主体时代迁移
  过来的那份）里没有 —— 直接显示会变成「套餐待生成」，哪怕方案早就生成、甚至已付过款。启动时
  按每个主体的存档现算一次 `quoteFor(tier, addons)` 把 `tierName` 补上；`amount` **只在为 0 时**才补，
  付过款的金额不会被现算报价盖掉（`applications.patchOrderSummary`，自检覆盖）。
- **手机号**：新增主体**不预填**（`createApplication` 的订单摘要里手机号为空）；同号不能再建主体
  由**服务端**在诊断接口拦，前端把服务端原文显示在手机验证弹框里。

### 验收

- `npm run check:entry`（**43 项**）：在原有 39 项「存档 → 首屏落点」之外，新增 4 项多主体断言
  （迁移后顶栏显示主体名、主体列表只有 1 个、切到第二个主体落在它自己的步骤、已支付主体徽标与
  支付成功界面）。
- `npx tsx scripts/check-applications.ts`（**56 项**）：键空间 / 列表收口 / 上限与作废 / 名称派生 /
  迁移（逐键搬运、落点、幂等、写失败不删旧键、已有列表不再迁移）/ 初始化。
- `.mcp-work/verify-multi-app.mjs`（**18 项**，真机）：默认一个空白主体 → 新增到 5 个（到顶置灰）→
  改名 → 作废当前（两次确认）回到 4 个；老存档迁移成主体 #1 落 `#payment` → 新增主体 #2 落
  `#survey` → 来回切换各自回到自己的步骤；已支付主体：顶栏名字 + `#paid`、下拉里
  「已支付 · 办理中」+「已生效履约中」+ 套餐与价格、且没有「作废服务」入口；
  **老摘要缺 `tierName`（已支付）时从存档现算回填**，不再显示「套餐待生成」、金额与支付状态不被改掉。
- 其余 23 个浏览器验证脚本（诊断/方案页/PDF/委托书/上传/续期落点/锁定态…）全部通过。
- `.mcp-work/verify-app-switch-isolation.mjs`（**32 项**，真机）：**切换主体后数据不串场**——
  ① 三个主体（A 在方案页 / B 已支付 / C 空白）来回切换，页面只出现当前主体的诊断结论、经营范围、
  单号、订单号与支付状态，别人的一个都不出现，切回来数据仍在，各自主体的存档键也各是各的；
  ② 两个都停在填报页的主体各自带一份申报草稿，切换后表单只显示自己的申报名称；
  ③ 在一个主体的服务群里发言，切到另一个看不到、切回来还在（运行时按主体隔离）；
  ④ **走真实链路**：主体 1 填问卷 + 手机验证生成方案（单号 REC-FLOW-1 / 第一次诊断）→ 新增主体 2
  同样生成（REC-FLOW-2 / 第二次诊断）→ 来回切换，各自页面、问卷答案、委托单号与列表里的名字
  （按各自诊断更新）都只属于各自主体。

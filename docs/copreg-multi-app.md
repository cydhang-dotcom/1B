# 多主体申请（S3）

一个用户可以有**多个企业设立申请**（产品确认：最多 5 个），每个主体各自一套问卷、方案、
委托单、订单、申报资料与进度。本文记录**存档键空间与迁移规则**；代码本体是
`src/copreg/applications.ts`（纯逻辑，`scripts/check-applications.ts` 74 项离线自检）。

> **当前状态：多主体申请已开放**（`applications.MULTI_APPLICATION_ENABLED = true`，2026-09 恢复）。
> 顶栏渲染主体切换与「新增企业注册」，最多 5 个主体。
> 曾经按产品要求屏蔽过一段时间（`false` 时顶栏不给入口、App 也拒绝新增，模型层保持完整）；
> 再需要屏蔽就把开关改回 `false` —— 真机脚本 `.mcp-work/verify-multi-app.mjs` 会按开关自动选模式，
> `scripts/check-copreg-entry.tsx` 里也有对应的一对断言（渲染/不渲染切换入口）。
>
> 进度：S3a（模型 + 存储键 + 迁移）、S3b（App 状态收敛）、S3c（顶栏切换/新增/改名/作废 + 各步骤按主体接线）、
> S3d（支付与路由按主体、验证与文档）均已实现；老存档在首次进入时自动迁移成「主体 #1」，用户无感。

## 一、键空间

| 键 | 内容 |
|---|---|
| `1b_copreg_apps_v1` | **主体列表**：每个主体一条 `ApplicationRecord`（id / 名称 / 创建与更新时间 / 当前步 / 解锁步 / 订单摘要 / 是否已提交申报资料） |
| `1b_copreg_active_app_v1` | 上次停留的主体 id（刷新按它恢复；**地址栏不带 appId**） |
| `1b_copreg_app:{id}:plan_form` | 该主体「填写的」：问卷 + 套餐 + 自选项（`planDraft.PlanForm`） |
| `1b_copreg_app:{id}:plan_report` | 该主体「返回的」：诊断结果（`PlanSuggestion`） |
| `1b_copreg_app:{id}:plan_record` | 该主体的委托单凭据 `{ recordId }` |
| `banbu-registration-{id}` | 该主体的申报资料表（第 5 步整份表单） |

旧的全局键（`1b_copreg_plan_form` / `_report` / `_record`、`banbu-registration-20260913-v1`）
**只留给迁移**，迁移成功后删除。

键工厂在 `applications.ts`：`planFormKey(id)` / `planReportKey(id)` / `planRecordKey(id)` /
`registrationKey(id)`；`planDraft.ts` 提供按主体读写的 `loadPlanDraftFor` / `savePlanFormFor` /
`savePlanReportFor` / `savePlanRecordFor` / `clearPlanDraftFor`（旧的全局函数保持原样，S3b 再切）。

## 二、业务规则（产品确认）

| 规则 | 落点 |
|---|---|
| **最多 5 个主体** | `MAX_APPLICATIONS = 5`；`addApplication` 到顶返回 `{ ok:false, reason:'limit' }`，UI 据此把「新增」置灰并说明 |
| **作废仅本地** | `discardApplication` 只删本地主体与存档，**不调任何接口**。注意：服务端那条 `recordId` 仍然存在，本地丢弃 ≠ 服务端撤单 |
| **已支付不可作废** | 订单摘要 `status === 'paid'` 时返回 `{ ok:false, reason:'paid' }` |
| **最后一个作废后补空白主体** | 列表永远不为空，避免出现「没有任何主体」的空壳界面 |
| **作废当前主体自动切走** | 切到剩下列表的第一个 |
| **主体之间不关联支付状态** | 每个主体各自一份订单摘要与 `recordId`；查单、下单、解锁都按各自的主体算 |
| **手机号不复用** | 新增主体**不预填**手机号；「同一手机号不能建第二个主体」由**服务端**在诊断接口拦（前端把服务端的原文显示在手机验证弹框里），以保持「手机号不落本地」的约定 |
| **名称可自定义** | 默认按 `申报表 basic.names[0]` → 诊断 `companyNameProposal` → 截断的 `companyDesc` → `企业设立申请（主体 N）` 派生；顶栏可改名（只落本地） |
| **申报资料按主体提交** | 仍走现有 `open-info { busUnionId, var2, savaType }`，每个主体用自己的 `recordId` |

## 三、没有老存档迁移（2026-10-08 已删除）

单主体时代的全局键（`1b_copreg_plan_form` / `_report` / `_record`、`banbu-registration-20260913-v1`）
与那套 `planLegacyMigration` / `applyLegacyMigration` **已经删掉**（按「去除旧的结构」的要求）：

1. 有主体列表 → 收口（`activeAppId` 无效时沿用列表里的第一个）；
2. 没有列表 → **全新的一份申请**，建一个空白主体、落第 1 步（不再去翻旧键）。

旧键**不读、不搬、也不删** —— 留着无害，硬删反而可能删掉别的页面还在用的东西。
`ensureApplicationsState` 是唯一入口，连空白主体都存不下时返回 `null`，由调用方提示。

## 四、实现要点（已落地）

- **App 状态收敛（S3b）**：`App.tsx` 只留两份状态 —— 持久化的主体列表 `applications + activeAppId`，
  以及每个主体的运行时 `AppRuntime`（`Record<appId, AppRuntime>`：问卷 / 方案 / 诊断建议 / 委托单 /
  订单详情 / 登记摘要 / 服务群消息 / 进度时间线 / 进度页演示态）。
  当前步骤、解锁范围、订单摘要、名称、是否已提交都在**主体记录**里，所以「刷新回到哪一步」与
  「切主体」用的是同一份数据；`activeAppId` 落 `1b_copreg_active_app_v1`，刷新回到上次那个主体。
- **地址栏语义**：hash 只反映「**当前主体**在哪一步」，**不带 appId**；切主体时地址栏会改成新主体的
  步骤。主体身份只由本地 `activeAppId` 决定 —— 分享出去的链接不会指向别人的主体。
- **顶栏（S3c，版式对照参考实现）**：品牌块（图标 + 「企业注册向导」+ AI 徽标 +
  「智能设立与合规规划服务」）+ 右侧切换按钮（楼宇图标 + 当前主体名 + 多于一个时的「N个主体」+ 箭头）。
  下拉标题是「我的企业注册服务（共 N 个）」，每条一张卡片：名称 + 「当前办理」徽标、
  「套餐: X · ¥Y」、右上状态徽标，底部一行创建时间与「作废服务 / 已生效履约中」，
  最下面一个虚线框按钮「新增企业注册」（到 5 个置灰并写明「已达上限」）。
  **相对参考实现的两处必要差异**：到顶置灰（参考没有上限）、每条多一个「改名」
  （参考不能改名，但产品要求名称可自定义）。作废仍要**点两次确认**、已支付不给入口；
  顶栏不再画进度条（参考也没有）。品牌块**纯展示、不可点**（原先点它回第 1 步，在第 5 步
  填报时容易误触，已去掉点击事件；顶栏只保留主体切换这一处交互）。
  下拉里的主体列表可以滚（`max-h-72`）：列表那段带 `.applications-scroll`，
  **滚动条常显**（`overflow-y: scroll` + 显式 `::-webkit-scrollbar`）—— Safari 的 overlay 滚动条
  默认只在滚动时出现，不这么写用户看不到「还有更多」（表头与「新增企业注册」按钮不跟着滚走）。
- **各步骤按主体接线（S3c）**：`RegistrationDetailsStep` / `AgreementAndPaymentStep` 接 `appId`，
  申报表读写走 `registrationStorageKey(appId)`；服务群消息、进度时间线、进度页演示态都按主体隔离，
  切主体不会串场。
- **支付按主体（S3d）**：订单状态核实的 checker 改成 **`Map<recordId, checker>`** —— 每个委托单号
  各自单飞，切主体互不影响，也不会重复查同一个单号。**付款成功要把「已支付」写回主体记录的
  订单摘要**（`applications.applyPaidOrder`：状态置 paid、单号/支付时间/手机号有才写、金额与套餐名
  一律不动、顺手解锁 `group`）—— 只更新运行时那份 `order` 是不够的，顶栏徽标、已支付不给作废、
  以及支付成功页新开填报页的深链放行读的都是那份摘要（2026-10 修的 bug，见「验收」里的
  `verify-header-live-status.mjs`）。
- **摘要回填**：`order.tierName` 是「下拉显示套餐」才加进摘要的，早于它的存档（含单主体时代迁移
  过来的那份）里没有 —— 直接显示会变成「套餐待生成」，哪怕方案早就生成、甚至已付过款。启动时
  按每个主体的存档现算一次 `quoteFor(tier, addons)` 把 `tierName` 补上；`amount` **只在为 0 时**才补，
  付过款的金额不会被现算报价盖掉（`applications.patchOrderSummary`，自检覆盖）。
- **手机号**：新增主体**不预填**（`createApplication` 的订单摘要里手机号为空）；同号不能再建主体
  由**服务端**在诊断接口拦，前端把服务端原文显示在手机验证弹框里。
- **跨标签页落盘是「合并写」，不是整份覆盖**（2026-10-08）：整份主体列表是**一个** localStorage 键，
  而用户会**新开标签页**去填申报资料（支付成功页的「申报资料填报」）、在原标签页切主体或新增主体。
  于是每个标签页手里都有一份**可能过期**的列表快照。`mergeApplicationsWrite(stored, mine, intent)` 的口径：
  1. 以**存档里当前那份**为基准（后写的标签页不会把别人刚加的删掉）；
  2. 只覆盖 `intent.dirtyAppIds` 里「本标签页这次真改过的那几条」；
  3. `intent.removedAppIds` 里的删掉；
  4. `activeAppId` **只有本标签页自己切过主体时才写**（`takeActiveAppId`）—— 否则填报页保存一次
     就把「当前主体」拽回它启动时的那个，用户的切换意图白点了。
  `App.tsx` 用一个 `writeIntentRef`（`dirty` / `removed` / `takeActive`）在**动作发生时**打标：
  `updateActiveApp`、`handleRenameApplication` → dirty；`handleDiscardApplication` → removed；
  `handleSwitchApplication`、**`handleAddApplication`（新增会顺手换当前主体）**、
  **作废的正是当前主体时**、`handleConfirmRecordDeleted` → takeActive。
  注意**申报草稿与接口参数本来就按各自 `appId` / `busUnionId` 走**（`banbu-registration-{appId}`），
  所以「保存会不会串到新主体」的答案是不会 —— 会坏的一直只是这份列表快照。

### 验收

- `npm run check:entry`（**62 项**）：存档 → 首屏落点、多主体断言（顶栏显示主体名、主体列表只有 1 个、
  切到第二个主体落在它自己的步骤、已支付主体徽标与支付成功界面），以及第 5 步深链与名称占位的渲染断言。
- `npx tsx scripts/check-applications.ts`（**74 项**）：键空间 / 列表收口 / 上限与作废 / 名称派生 /
  **合并写**（只覆盖改过的那几条、别人新增的不丢、`activeAppId` 只在自己切过主体时才动、
  没改动就不写、空列表回落到空白主体）/ **付款成功写回摘要**（置 paid、单号/时间/手机号有才写、
  空串不覆盖、金额与套餐名不动、`group` 不写重复、纯函数不动原记录）/ 初始化。
  **没有迁移那一段了**（见 §三）。
- `.mcp-work/verify-multi-app.mjs`（**18 项**，真机）：默认一个空白主体 → 新增到 5 个（到顶置灰）→
  改名 → 作废当前（两次确认）回到 4 个；新增主体落 `#survey` → 来回切换各自回到自己的步骤；
  已支付主体：顶栏名字 + `#paid`、下拉里「已支付 · 办理中」+「已生效履约中」+ 套餐与价格、
  且没有「作废服务」入口；**摘要缺 `tierName`（已支付）时从存档现算回填**，不再显示「套餐待生成」、
  金额与支付状态不被改掉。
- `.mcp-work/verify-cross-tab-apps.mjs`（**13 项**，真机 · 跨标签页）：两个标签页共用一个 localStorage ——
  标签页 B 是「支付成功页新开的填报页」（会话钉在自己的主体上），标签页 A 在原页面**切主体 + 新增主体**，
  这时回到 B **保存草稿 + 改名**：保存请求带的是 B 自己的 `busUnionId`、草稿写在自己的键下、
  B 的页面不跟着切；B 落盘后**3 个主体都还在、`activeAppId` 仍是 A 新增的那个**、别人那条没被覆盖。
  把落盘退回「整份快照盖上去」的旧口径跑一遍，最后三条会红（已实测）——这条自检就是钉住这个回归的。
- `.mcp-work/verify-header-live-status.mjs`（**15 项**，真机 · 顶栏状态实时更新，2026-10 新增）：
  A 在支付页走完真实付款链路（桩下单 + 查单：进页面时 status '0'，点过「立即支付」才回 '1'）——
  断言界面翻成支付成功、**顶栏那一条同步显示「已支付 · 办理中」「已生效履约中」且不再有「作废服务」**、
  存档摘要落成 paid（单号写回、**已付金额不被现算报价盖掉**）、解锁 group；B 顺着 A 的结果新开
  `?open=fill-details` 的标签页，深链被放行（落第 5 步、参数已抹）；C 对照主体仍是「待支付」+ 留着
  「作废服务」（状态没写串）；D 覆盖**别的状态**：切档后顶栏套餐 / 价格实时跟着翻（¥600 → ¥2500）
  并落进摘要，前往支付后步骤徽标从「方案待确认」翻成「待支付」。
  **把付款写回摘要那一步去掉（退回只 `unlockStep('group')`）跑一遍，A/B 两段共 4 条会红（已实测）**。
- 其余浏览器验证脚本（诊断/方案页/PDF/委托书/上传/续期落点/锁定态…）全部通过；
  `.mcp-work/verify-app-switch-isolation.mjs` **32 项 + 1 项跳过**（见下）。
- `.mcp-work/verify-app-switch-isolation.mjs`（真机）：**切换主体后数据不串场**——
  ① 三个主体（A 在方案页 / B 已支付 / C 空白）来回切换，页面只出现当前主体的诊断结论、经营范围、
  单号、订单号与支付状态，别人的一个都不出现，切回来数据仍在，各自主体的存档键也各是各的；
  ② 两个都付过款的主体各自带一份申报草稿：从支付成功页走**深链**（`?open=fill-details`，第 5 步现在
  只有这一个入口）进填报页，表单只显示自己的申报名称；切主体后**落回各自的支付成功页**
  （第 5 步是会话级位置，不跟着串），再进填报页又是自己的那份；
  ③ **跳过**（1 项）：在服务群里发言、切主体看不到、切回来还在 —— 现在**第 4 步从支付成功页没有入口**
  （只有「进度页 → 进入服务群」那条链，而进度页本身也只能从进度页的入口进），`__sendChat` 找不到
  群聊输入框，脚本如实跳过并打印原因，**不假装通过**；入口定下来后把那段断言放回去即可；
  ④ **走真实链路**：主体 1 填问卷 + 手机验证生成方案（单号 REC-FLOW-1 / 第一次诊断）→ 新增主体 2
  同样生成（REC-FLOW-2 / 第二次诊断）→ 来回切换，各自页面、问卷答案、委托单号与列表里的名字
  （按各自诊断更新）都只属于各自主体。
